## 1. Огляд системи

GoPadel - мультисервісна платформа на .NET 9 для бронювання кортів падел-тенісу.

| Сервіс | Тип | Відповідальність |
|--------|-----|------------------|
| GoPadel.Api | REST API | Бронювання, користувачі, матчі, клуби, корти, події, міста |
| GoPadel.Chat | SignalR сервіс | Чат у реальному часі |
| GoPadel.Payment | REST API | Обробка платежів через LiqPay, вебхуки |
| GoPadel.Admin | REST API | Адміністративні операції |
| GoPadel.Web | Razor Pages | Адмін-портал / портал партнерів |
| GoPadel.BookingsJob | Console App | Фонові задачі по бронюванням |
| GoPadel.DataAccess | Бібліотека | Репозиторії (Dapper + SQL Server) |
| GoPadel.Infrastructure | Бібліотека | Міграції, спільні утиліти |
| GoPadel.PushNotifications | Бібліотека | Push-повідомлення через Expo |
| GoPadel.Sanity | Бібліотека | Інтеграція з Sanity CMS |

**Поточний стан:** Автоматизовані тести відсутні. Цей документ визначає стратегію тестування для впровадження.

## 5. Повні користувацькі сценарії (E2E)

### Сценарій 1: Новий користувач бронює та оплачує корт

```
Реєстрація -> Заповнення профілю -> Перегляд клубів -> Вибір корту ->
Створення бронювання -> Оплата через LiqPay -> Отримання підтвердження ->
Перегляд у "Мої бронювання"
```

| Крок | Дія | Сервіс | Перевірка |
|------|-----|--------|-----------|
| 1 | Реєстрація через Firebase | Api + Firebase | Користувач створений в БД, JWT повернено |
| 2 | Заповнення профілю | Api | Профіль збережено, повертає 200 |
| 3 | Перегляд клубів у Києві | Api | Список клубів відфільтрований за містом |
| 4 | Отримання доступних кортів | Api | Доступні слоти для обраної дати |
| 5 | Створення бронювання | Api + DataAccess | Бронювання створено, статус = "Очікує оплати" |
| 6 | Ініціювання оплати | Payment | URL перенаправлення LiqPay згенеровано |
| 7 | Завершення оплати | Payment (webhook) | Транзакція записана, бронювання = "Підтверджено" |
| 8 | Push-повідомлення | PushNotifications | Повідомлення про підтвердження доставлено |
| 9 | Перегляд бронювання | Api | Бронювання видно у списку зі статусом "Підтверджено" |

### Сценарій 2: Скасування бронювання з поверненням коштів

```
Існуюче бронювання -> Запит на скасування -> Ініціювання повернення ->
Оновлення бронювання -> Push-повідомлення
```

| Крок | Дія | Сервіс | Перевірка |
|------|-----|--------|-----------|
| 1 | Відкрити підтверджене бронювання | Api | Деталі бронювання повернуто |
| 2 | Запит на скасування | Api | Перевірка допустимого терміну скасування |
| 3 | Обробка повернення коштів | Payment | Виклик LiqPay refund API, запис повернення |
| 4 | Оновлення статусу | Api + DataAccess | Статус бронювання = "Скасовано" |
| 5 | Відправка повідомлення | PushNotifications | Повідомлення про скасування відправлено |

### Сценарій 3: Чат між гравцями в реальному часі

```
Гравець A відкриває чат -> Відправляє повідомлення -> Гравець B отримує в реальному часі ->
Гравець B відповідає -> Push-повідомлення якщо офлайн
```

| Крок | Дія | Сервіс | Перевірка |
|------|-----|--------|-----------|
| 1 | Гравець A підключається до SignalR | Chat | З'єднання встановлено |
| 2 | Гравець A відправляє повідомлення | Chat + DataAccess | Повідомлення збережено, доставлено через hub |
| 3 | Гравець B отримує повідомлення | Chat (SignalR) | Повідомлення з'являється в реальному часі |
| 4 | Гравець B йде офлайн | - | SignalR від'єднано |
| 5 | Гравець A відправляє ще повідомлення | Chat + PushNotifications | Повідомлення збережено, push-повідомлення відправлено |

### Сценарій 4: Адміністратор керує клубами та кортами

```
Вхід адміна -> Створення клубу -> Додавання кортів -> Налаштування доступності ->
Перевірка відображення у додатку користувача
```

| Крок | Дія | Сервіс | Перевірка |
|------|-----|--------|-----------|
| 1 | Вхід адміна на web-портал | Web + Auth | Дашборд завантажено |
| 2 | Створення нового клубу | Admin + DataAccess | Клуб збережено в БД |
| 3 | Додавання кортів до клубу | Admin + DataAccess | Корти прив'язані до клубу |
| 4 | Користувач шукає клуби в місті | Api | Новий клуб з'являється в результатах |
| 5 | Користувач бачить доступні корти | Api | Нові корти доступні для бронювання |

## 6. Інтеграція в CI/CD (Azure DevOps)

### Архітектура пайплайну

```
Тригер (push/PR)
  -> Етап 1: Build
    -> Збірка рішення
    -> Unit Tests
  -> Етап 2: Integration Tests
    -> Запуск SQL Server контейнера
    -> Інтеграційні тести
  -> Етап 3: QA
    -> Деплой на QA середовище
    -> API Tests
    -> Selenium Tests
  -> Етап 4: Staging
    -> Деплой на Staging
    -> Performance Tests
  -> Етап 5: Production
    -> Ручне підтвердження (approval gate)
    -> Деплой на Production (slot swap, zero-downtime)
```

### Опис етапів пайплайну

#### Етап 1: Build & Unit Tests

- **Тригер:** push в master, develop, feature/* або створення PR
- **VM Image:** ubuntu-latest
- **Кроки:**
  1. Встановлення .NET 9 SDK
  2. Відновлення NuGet пакетів (`dotnet restore`)
  3. Збірка рішення (`dotnet build --configuration Release`)
  4. Запуск Unit Tests (`dotnet test GoPadel.Tests.Unit`)
  5. Публікація результатів тестів (формат TRX -> вкладка Tests)
  6. Публікація Code Coverage (Cobertura -> вкладка Code Coverage)
  7. Публікація артефактів збірки (publish кожного сервісу)

#### Етап 2: Integration Tests

- **Залежність:** успішне завершення Етапу 1
- **Сервіси:** SQL Server 2022 контейнер (Testcontainers або Docker service)
- **Кроки:**
  1. Встановлення .NET 9 SDK
  2. Запуск інтеграційних тестів з підключенням до SQL Server
  3. Публікація результатів тестів

#### Етап 3: QA - API Tests + Selenium

- **Залежність:** успішне завершення Етапу 2
- **Умова:** тільки для master гілки
- **Кроки:**
  1. Деплой API та Web на QA середовище (Azure Web App)
  2. Запуск API тестів проти QA середовища
  3. Встановлення Chrome (headless) для Selenium
  4. Запуск Selenium тестів проти QA Web порталу
  5. Публікація результатів усіх тестів

#### Етап 4: Staging & Performance Tests

- **Залежність:** успішне завершення Етапу 3
- **Кроки:**
  1. Деплой на Staging середовище
  2. Встановлення k6 (інструмент навантажувального тестування)
  3. Запуск навантажувальних тестів (load-test.js)
  4. Публікація результатів продуктивності

#### Етап 5: Production Deployment

- **Залежність:** успішне завершення Етапу 4
- **Умова:** тільки master гілка + ручне підтвердження
- **Стратегія:** zero-downtime через Azure slot swap
- **Кроки:**
  1. Деплой на staging слот Production App Service
  2. Swap staging -> production слот

### Необхідне налаштування Azure DevOps

1. **Service Connection:** Створити Azure Resource Manager service connection `GoPadel-Azure-ServiceConnection`
2. **Environments (середовища):**
   - `GoPadel-QA` - автоматичний деплой
   - `GoPadel-Staging` - автоматичний деплой
   - `GoPadel-Production` - з ручним підтвердженням (approval gate)
3. **Variable Groups (групи змінних):** Зберігати секрети в Azure DevOps Library:
   - `GoPadel-QA-Variables` - connection strings, Firebase ключі для QA
   - `GoPadel-Staging-Variables` - конфігурація Staging
   - `GoPadel-Production-Variables` - секрети Production
4. **Звітність тестів:** Результати публікуються автоматично через задачу `PublishTestResults@2`, видно у вкладці Tests кожного запуску
5. **Code Coverage:** Звіти покриття коду у вкладці Code Coverage після unit тестів
6. **Branch Policies (політики гілок):** Налаштувати для master:
   - Обов'язковий PR з мінімум 1 рецензентом
   - Збірка повинна бути успішною (етапи Build + Integration)
   - Всі коментарі повинні бути вирішені

### Quality Gates (шлюзи якості)

| Шлюз | Поріг | Етап |
|------|-------|------|
| Успішність Unit тестів | 100% | Build |
| Покриття коду | >= 70% | Build |
| Успішність Integration тестів | 100% | Integration |
| Успішність API тестів | 100% | QA |
| Успішність Selenium тестів | 100% | QA |
| Час відповіді API p95 | < 500мс | Staging |
| Критичні вразливості | 0 | Усі етапи |
